# 01-ssh-bruteforce.md

## 1. Метаданные
| Поле                 | Значение                              |
| -------------------- | ------------------------------------- |
| Дата                 | 2026-10-30                            |
| Техника ATT&CK       | T1110                                 |
| Подтехника           | T1110.001 (Password Guessing)         |
| Тактика              | Credential Access, Lateral Movement   |
| Инструмент атаки     | Hydra                                 |
| Источник (атакующий) | 10.10.10.102 (Kali)                   |
| Цель                 | lin-cl01 (10.10.10.100), Debian 12    |
| Источник логов       | /var/log/auth.log (sshd), Wazuh agent |

## 2. Хронология (таймлайн)

| Время       | Событие                                                               | rule.id | rule.level | Источник               |
| ----------- | --------------------------------------------------------------------- | ------- | ---------- | ---------------------- |
| 11:40:53    | Серия Failed password для invalid user ivan/admin                     | 5710    | 5          | auth.log (sshd)        |
| 11:40:53–54 | Повторяющиеся неудачные попытки с 10.10.10.102                        | 5710    | 5          | Wazuh alert            |
| —           | Срабатывание агрегирующего правила (8+ попыток / 120 сек, один srcip) | 5712    | 10         | Wazuh alert            |
| —           | Успешный вход testuser после серии неудач                             | 40101   | 12         | auth.log / Wazuh alert |

Примечание: атака запускалась несколько раз в ходе отладки; точный таймлайн чистого прогона не зафиксирован отдельно, итоговые rule.id подтверждены по нескольким запускам.

## 3. Обнаружение (Detection)
- **rule.id 5710** (level 5) — отдельные неудачные попытки входа с указанием invalid user, базовое правило sshd
- **rule.id 5712** (level 10) — "sshd: brute force trying to get access", срабатывает по `if_matched_sid 5710`, порог: 8 попыток за 120 секунд с одного source IP, применимо только к попыткам с несуществующим пользователем
- **rule.id 40101** (level 12) — "System user successfully logged", фиксирует успешный вход
- MITRE-метка в Wazuh для 5712 (T1110) корректна и совпадает с фактической техникой
- Важный нюанс: правило 5712 не сработает при атаке на **существующего** пользователя (testuser), так как такие попытки обрабатываются другим правилом (valid user), не связанным с 5710/5712

## 4. Реагирование (Response)
- Active Response (firewall-drop) настроен: command зарегистрирован, active-response блок с `rules_id: 5712`, затем `5710`, `location: local`, `timeout: 600`
- **Не сработал end-to-end.** Диагностика:
  - execd стабильно работает, скрипт firewall-drop исполняемый и корректно обрабатывает валидный JSON при ручном тесте
  - При реальном срабатывании 5712 скрипт получал JSON с ошибкой "Invalid input format"
  - После переключения на rules_id 5710 команда не отправлялась агенту вовсе (active-responses.log пуст при подтверждённом алерте в дашборде)
  - Версия Wazuh: 4.14.9-rc2 (release candidate) — вероятная причина: несовместимость сериализации алертов analysisd с ожиданиями скрипта в этой сборке
- Полная цепочка диагностики — см. Приложение
- L1 в текущих условиях: заблокировать IP вручную (iptables/firewall), так как автоматическое реагирование недоступно

## 5. Оценка (Verdict)
**True Positive.** Подтверждено прямым сопоставлением алертов Wazuh с сырыми записями auth.log; успешный вход testuser после серии неудач с того же IP — явный индикатор компрометации учётной записи.

## 6. Находки (Findings)
- Правило 5712 корректно классифицирует T1110, но имеет узкую область действия (только invalid user), что создаёт слепую зону при атаке на существующие учётные записи
- OpenSSH `MaxStartups` (лимит одновременных неаутентифицированных соединений) и `MaxAuthTries` могут искажать картину атаки с высокой степенью параллелизма инструмента — важно учитывать при подборе числа потоков brute-force утилиты
- Active Response, несмотря на корректную конфигурацию на всех проверяемых уровнях, не сработал — возможный баг release candidate сборки Wazuh

## 7. Рекомендации
- Для продакшена: проверить, покрывает ли используемый SIEM атаки на существующие учётные записи отдельным правилом (не полагаться только на правило для invalid user)
- Протестировать Active Response на стабильном релизе (не rc) перед внедрением в реальную инфраструктуру
- Рассмотреть добавление правила/корреляции на успешный вход после N неудач именно для **существующих** пользователей, если такого нет в используемом наборе правил

## Приложение: Диагностика Active Response

1. Конфигурация `<active-response>` изначально была случайно обёрнута в XML-комментарий (`<!-- -->`) при правках, из-за чего менеджер полностью игнорировал блок, несмотря на корректный синтаксис внутри
2. После снятия комментария: command `firewall-drop` подтверждён зарегистрированным, execd запускается стабильно при каждом рестарте менеджера
3. Групповая конфигурация для агента (`agent.conf`) через `/var/ossec/etc/shared/default/agent.conf` — рабочий способ доставки active-response конфигурации на агента (в отличие от прямого редактирования `/var/ossec/etc/shared/ar.conf`, который является служебным файлом, перегенерируемым менеджером)
4. При срабатывании rules_id 5712: скрипт получал запрос, но падал с "Invalid input format" — ручной тест с синтетическим корректным JSON прошёл успешно (скрипт ответил `check_keys`), что указывает на несоответствие между реальным форматом алерта от analysisd и ожиданиями скрипта
5. Переключение на rules_id 5710 не решило проблему — команда не отправлялась агенту вовсе, при этом сам алерт 5710 подтверждённо фигурировал в дашборде
6. Итоговый вывод: причина, вероятнее всего, в версии 4.14.9-rc2 (release candidate); дальнейшее расследование остановлено как не являющееся приоритетным для целей лабораторной практики детектирования
